02 What the app is for

A shop or a factory keeps stock. Stock is money sitting on a shelf. There are two ways to lose that money.

  • Too little stock. A customer wants to buy, you have none, you lose the sale.
  • Too much stock. Your money is stuck in boxes. It may go out of date and become worthless.

OptiStock helps find the middle. It watches what sells, predicts what will sell next, and tells you what to order.

See it working

Open https://optistock.duckdns.org and sign in. The Purchase orders screen is this idea made real: it says what to buy next, and why.

04 Containers and Docker

The idea, in one sentence

A container is a small box that holds a program and everything it needs to run. Move the box to any computer and the program still works.

Before containers, developers said "but it works on my machine". The other machine had a different Python, or a missing library. A container ends that argument, because the box carries its own copy of everything.

Your project has six boxes running at the same time. The file that lists them is docker-compose.yml.

A detail worth knowing

api, relay and consumers are the same program, started three different ways. They are kept separate because they fail differently. If you restart the alert rules, message delivery should not stop.

05 What an API really is

An API is just a list of addresses the server understands. Nothing more mysterious than that. 

GET  /api/v1/products/        give me the products
POST /api/v1/sales/           record a sale
GET  /api/v1/alerts/          what needs attention

GET means "give me something". POST means "here is something new". The browser sends one of these, the server replies with data, and the screen draws it.

In your project, each area of the business has its own folder inside app/modules/, and each folder has the same four files:

models.py what the data looks like in the database
schemas.py what the data looks like coming in and going out
service.py the actual rules and thinking
router.py the addresses, like /api/v1/sales/
Why split into four files

So each file has one job. When a sale is wrong, you look in service.py. When an address is wrong, you look in router.py. You never have to read all of it.

06 Transactions: all or nothing

The idea

A transaction is a group of database changes that must all succeed, or none of them must.

Think of moving money between two bank accounts. Take ₹100 out of one, put ₹100 into the other. If the computer dies in the middle, you must not end up with the money taken out but never arriving.

A sale in your app is the same. It writes a sale row, and it reduces the stock. Those two must happen together, or the numbers lie.

A rule your project follows everywhere

The service.py files never decide when to save. The router.py owns that. One place decides, so a transaction can never be half-finished by accident.

07 Keeping companies apart

Your app serves more than one company from one database. TechNova and GreenLeaf both have products, both have sales, all in the same tables.

What keeps them apart is a single column on every table: company_id. 

-- correct: only this company's products
SELECT * FROM products WHERE company_id = 'technova';

-- forget one line, and TechNova sees GreenLeaf's business
SELECT * FROM products;
The most dangerous bug in this whole project

Forgetting that filter does not crash. Nothing turns red. The page just quietly shows another company their competitor's data. This is why the tests check it, and why every query in the code filters on it.

There is a second layer of safety. When you log in you get a token — a signed note saying who you are. The server does not simply trust it: 

# app/core/dependencies.py
user = db.query(User).filter(User.id == user_id).first()
if str(user.company_id) != company_id:
    raise HTTPException(401, "Invalid token payload")

The token says "I belong to TechNova". The server checks the database and asks: is that still true? If someone edits their token, it fails here.

08 Events and the outbox

This is the hardest idea in your project. Take it slowly. It is worth it, because this is real senior-level engineering and you built it.

First: what is an event?

An event is a note saying something happened. "Stock fell below the reorder point." Other parts of the system read these notes and react, without the sale having to know about them.

Why bother

Without events, the sale code would have to raise the alert, update the dashboard, and send the email itself. Every new feature would mean editing the sale code again. With events, the sale just says what happened, and new features listen.

Now: the problem

Saving the sale and sending the note are two different systems — the database and the message queue. You must do one first. Both orders are broken.

Because the note is a row in the same database, the transaction from Lesson 6 covers both. They cannot disagree.

app/modules/events/publisher.py writes the note
app/workers/relay.py sends the notes out later
One more thing to understand

The relay sends the note, then marks it as sent. If it crashes in between, the note gets sent twice. That is on purpose. Every note carries an ID so a repeat can be ignored — and a repeated message can be spotted, while a lost message cannot.

09 Background workers

A worker is a program with no web address. Nobody visits it. It just runs in a loop, doing a job.

Your project has two, plus a nightly job:

relay.py reads unsent notes, pushes them to Redis
consumers.py reads notes from Redis, raises alerts
app/core/scheduler.py runs the analytics every night at 01:00
Why not do this during the request?

Because the customer would wait. The sale replies in about 50 milliseconds. Raising alerts and recalculating dashboards happens after they have already got their answer.

10 The analytics side

Reading a year of sales is slow. If a report did that on the live database, every user would feel it. So the history is copied out each night into separate files.

ABC classes

Sort products by money earned, biggest first. The products making the first 80% of the money are class A — watch these closely. Up to 95% is B. The long tail is C.

The forecast

This is not artificial intelligence, and your code is honest about that. It is an average: 

average daily sales = units sold in the last 30 days / 30
A small detail that matters a lot

Divide by 30, not by "days that had a sale". If a product sold 5 units on one day only, dividing by 1 says it sells 5 a day. Dividing by 30 says it sells 0.17 a day. The second one is the truth.

11 Getting it on the internet

When you type git push, a robot on GitHub wakes up and does four things in order. If any step fails, it stops.

A real failure that happened to you

One deploy showed a green tick but had shipped nothing. The git pull step failed, the script ignored it, and it rebuilt the old code. Everything after that looked healthy — because it was healthy. It was just the wrong version.

The fix is one line: set -euo pipefail. It means "stop at the first thing that fails". A deploy that cannot fail is not a deploy.

HTTPS, and why it matters

Without it, a password travels across the internet as readable text. HTTPS locks it. Your site has it, free, from a service called Let's Encrypt, and it renews itself every 90 days.

12 Not losing everything

Three safety nets, and all three were tested for real.

Backups

Every night the database is copied to Amazon S3, away from the server. If the server is destroyed, the data survives. One backup was actually restored into a spare database and every table matched.

A backup you have never restored is only a hope. That is why it was tested.

Rollback

One command puts the previous version back, in about four minutes. This was also tested on the live site — back, then forward again, with no downtime.

Tests

446 automatic checks. They run before every deploy. If one fails, nothing reaches the server.

The important trick: a test is only useful if it can fail. To prove the new tests worked, the code was deliberately broken three times to check each break was caught.

What is still missing

There is one server. If it dies, the site is down until it is rebuilt (the data is safe). Fixing that costs money, so it is a fair trade for a demo — but you should know it, rather than discover it.
