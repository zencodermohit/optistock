OptiStock, one scan at a time

Every stock movement is written exactly once. Everything that reacts to it — alerts, dashboards, forecasts — runs afterwards, so nothing that reacts can ever make the scanner wait.

Follow one scan, in eight steps

The numbers on the diagram are in the order things actually happen. Notice that step 4 — answering the device — comes before steps 5 to 8.

  1. 1Somebody scans a carton A reader sends the SKU, the warehouse, in-or-out, and a quantity.
  2. 2It arrives at one endpoint Through nginx, then /api/v1/ingest/scan. The token says which company this is, and it is checked against the live database row, not just trusted.
  3. 3One commit changes two things The stock level changes and an outbox row is written, inside a single database transaction. Both land, or neither does. There is no moment where stock has moved but nobody was told.
  4. 4The device is answered and let go About 200 ms. Everything after this happens with nobody waiting on it.
  5. 5A separate worker picks the row up The relay claims unpublished outbox rows with FOR UPDATE SKIP LOCKED, so two copies of it never grab the same row. It publishes first and marks the row done second — that order is deliberate.
  6. 6The event goes onto the queue An XADD into the Redis stream optistock:events.
  7. 7Consumers read it back out An XREADGROUP from the consumer group. They commit their work first and acknowledge second, so a crash in between simply redelivers the message.
  8. 8The alert lands in the database And the next dashboard read — the third column — shows it on the screen.

Three questions worth being ready for

Why not just send the alert directly?

Because then a slow or broken alert would hold up the scan. Worse, if the alert failed after the stock had already changed, the two would silently disagree forever. Writing the outbox row in the same commit makes that impossible: they succeed together or fail together.

This pattern has a name — the transactional outbox.

What if the same event is delivered twice?

It will be, eventually — the relay can crash after publishing but before marking the row done. That is why the guarantee is at least once, not exactly once, and why every handler is written to tolerate seeing an event it has already handled.

The same idea protects the device: replaying a scan returns the original answer.

Where is the machine learning?

There isn’t any, on purpose. The forecast is a moving average and the reorder maths is the textbook EOQ, safety-stock and reorder-point formulas. They are explainable, they need no training data, and on this dataset they are hard to beat.

The assistant uses a language model, but only to read and explain — never to decide.

True at every layer

  • One tenant at a timeThe company comes from the token and is re-checked against the live row. Every query, every event and every assistant tool is scoped to it.
  • Nothing is anonymousA JWT is required at the edge. There is no unauthenticated way in.
  • Requests are counted per callerRate limiting keys on the real client address, not on the proxy in front of it — otherwise every user shares one bucket.
  • Handlers expect repeatsAt-least-once delivery means doing the same work twice must be harmless.
  • Every change leaves a traceWrites are recorded in audit_logs, so any number on a screen can be traced back to what caused it.
