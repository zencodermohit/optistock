Almost every design decision in this project comes from the same question, asked in different places: what happens when this fails half way through? Read it with that in mind and the architecture stops looking elaborate and starts looking inevitable.

PART 1Follow one scan

The fastest way to understand a system is to follow one piece of data all the way through it. So: somebody in the Mumbai warehouse scans a barcode as a carton goes out. Here is every place that scan touches, in order.

What each stop is really doing

1. The scanner sends three facts. What, where, which way. Nothing else. A barcode gun, an RFID gateway or an ESP32 can all produce those, which is what makes the hardware interchangeable — the API speaks the reader's vocabulary, not the database's. 

POST /api/v1/ingest/scan
{ "sku": "ELEC-LAP-001-A", "warehouse_id": "...", "direction": "out",
  "quantity": 1, "scan_reference": "A17" }

2. Nginx terminates TLS, throttles, and passes the request on. It also sets X-Real-IP, which turns out to matter a great deal — see §7.

3. FastAPI turns the token into a tenant. The company_id comes from the signed token, never from the request body. §1.

4. Idempotency. The device supplied scan_reference: "A17". If a movement with that reference already exists, the endpoint returns the original answer and moves nothing. A radio that retries, or a trigger held a beat too long, therefore costs nothing.

5. One transaction. The stock change and the announcement of it are written together. This is the keystone — §2.

6–8. A separate process carries the announcement to Redis; consumers read it and react. The scanner is long gone by then. That is why a slow alert never slows a scan.

MECHANISM 1The tenant boundary

One database holds several companies. Every row that belongs to somebody carries a company_id, and the entire security model reduces to one sentence: that value is never taken from the request. 

payload = jwt.decode(token, settings.SECRET_KEY, algorithms=[settings.ALGORITHM])
user_id    = payload.get("sub")
company_id = payload.get("company_id")
...
user = db.query(User).filter(User.id == user_id).first()
if not user or not user.is_active:
    raise HTTPException(status_code=401, detail="Inactive or unknown user")
if str(user.company_id) != company_id:
    raise HTTPException(status_code=401, detail="Invalid token payload")
app/core/dependencies.py

Why check the database when the token is already signed?

A signed token proves the server issued it. It does not prove the claim is still true. Between issuing and using, an account can be deactivated or moved to another company — and a token is valid until it expires no matter what happened in between. Re-reading the user costs one indexed lookup and closes the window where a sacked employee's laptop still works.

Downstream, nothing has to remember this. The assistant's tools are built as closures with the company already bound inside them, so the model literally cannot supply a tenant — the argument does not exist in any signature it can see.

MECHANISM 2The outbox

When stock moves, two things must happen: the number changes, and everyone who cares finds out. The obvious implementation is to update the row and then publish a message. It has a failure that cannot be engineered away:

OrderWhat goes wrong
commit, then publishProcess dies in between. Stock changed, nobody was told. The alert never fires and nothing anywhere records that it should have.
publish, then commitTransaction rolls back. An alert fires for a movement that never happened.

There is no third ordering. A database commit and a network send cannot be made atomic with each other — so the fix is to stop trying, and make the message a database write too: 

class EventOutbox(Base):
    sequence     = Column(BigInteger, primary_key=True, autoincrement=True)
    event_id     = Column(UUID(as_uuid=True), default=uuid.uuid4, nullable=False)
    company_id   = Column(...)
    published_at = Column(DateTime(timezone=True), nullable=True)
app/modules/events/models.py

Now both writes are in one transaction. Either both survive or neither does. A separate process — the relay — reads unpublished rows and carries them out to Redis.

Two details in that model worth noticing

published_at is a timestamp, not a boolean. "Published" and "published at 14:32:07" cost the same to store, and only one of them can answer "how far behind is the relay right now?"

sequence is an auto-incrementing integer, so events have a total order independent of clocks. Two servers with slightly different times cannot disagree about which movement came first.

MECHANISM 3At-least-once, and living with it

The relay claims a batch, publishes it, and only then marks it published.

SELECT ... FROM event_outbox
WHERE published_at IS NULL
ORDER BY sequence
FOR UPDATE SKIP LOCKED

FOR UPDATE means two relays cannot publish the same row. SKIP LOCKED means the second relay takes the next batch instead of blocking on the first one's locks. Together they make the relay horizontally scalable without any coordination.

Publish first, mark second — a deliberate choice of failure

If the process dies between the two, the event is published twice on restart. Marking first would give the opposite: an event published zero times. Both are failures; they are not equally bad. A duplicate carries an event_id, so a consumer can recognise it and discard it. A lost event leaves nothing behind to notice — no row, no log, no gap. You cannot write code that detects an absence you have no record of.

Duplicates therefore have to be harmless, which shows up twice in this system: consumers de-duplicate on event_id, and the scan endpoint de-duplicates on the device's own scan_reference. Same idea, two layers — one protects against the relay retrying, the other against the radio retrying.

MECHANISM 4The stream

Redis Streams rather than a plain list, because a list gives you no way to know whether a worker that took an item actually finished it. A consumer group tracks exactly that: 

self.redis.xgroup_create(STREAM_KEY, CONSUMER_GROUP, id="0", mkstream=True)
...
response = self.redis.xreadgroup(CONSUMER_GROUP, name, {STREAM_KEY: ">"}, ...)
...
self.redis.xack(STREAM_KEY, CONSUMER_GROUP, entry_id)
app/workers/consumers.py

An entry read but not acknowledged stays in the group's pending list. If the worker crashes half way through raising an alert, the entry is still there to be reclaimed — it is not quietly gone.

Handlers register themselves against event types, so adding a reaction never means editing the loop: 

@on(event_types.STOCK_BELOW_REORDER_POINT)
def raise_low_stock_alert(...): ...

@on(event_types.STOCK_DEPLETED)
def raise_stockout_alert(...): ...
app/modules/alerts/handlers.py

MECHANISM 5The night job

At 01:00 one job runs. It is one job rather than three timers for a specific reason: each stage reads what the last one wrote, and as independent jobs a slow ETL would leave the others analysing yesterday's data — silently, and correctly-looking. 

run_nightly_etl()                       # sales history → Parquet

abc_df      = run_abc_analysis()        # which items earn the revenue
forecast_df = run_demand_forecast()     # how fast each one sells

persist_abc_classes(db, abc_df)
persist_reorder_recommendations(db, forecast_df)
persist_forecast_runs(db, forecast_df)  # record tonight's predictions
score_due_forecasts(db)                 # grade the ones whose window closed
app/core/scheduler.py

The maths, in full

ABC sorts products by revenue and splits them by cumulative share — the few that earn most (A), the middle (B), the long tail (C). It is Pareto, applied to a catalogue.

The forecast is an average daily velocity over a fixed window:

velocity = units_sold_in_window / window_length_in_days

The divisor is the whole trick

Dividing by days that had a sale instead of the window length looks more precise and is catastrophically wrong. An item that sold 10 units on a single day of a 30-day window scores 10 units/day rather than 0.33 — a thirty-fold overestimate, which the reorder policy then multiplies into a purchase order. The fix is one denominator; the bug was invisible until somebody compared a recommendation with reality.

The reorder point is when to buy — enough to cover the wait for a delivery, plus a cushion for weeks busier than average:

reorder_point = daily_usage × lead_time + safety_stock

safety_stock  = (max_daily × max_lead_time) − (avg_daily × avg_lead_time)
app/modules/analytics/stockout.py · app/modules/analytics/eoq.py

EOQ — economic order quantity — is how much, balancing the cost of placing an order against the cost of holding stock:

EOQ = √( 2 × annual_demand × order_cost / holding_cost_per_unit )

An honest limitation, stated in the code itself

That safety-stock formula wants a maximum lead time as well as an average, and this schema cannot supply one: no purchase order records when a delivery was promised versus when it actually landed. So the same average is passed for both, which collapses the formula to demand variability alone — (peak daily − average daily) × lead time — and under-covers a supplier who is late as well as busy.

The interesting part is that this is written down in the docstring rather than quietly tolerated. A figure that looks like it accounts for supplier reliability, but doesn't, is more dangerous than one that admits the gap.

Why no machine learning

Not because it would be hard. Because every number on the screen has to be defensible to the person acting on it. "Order 400" from a model nobody can interrogate is not advice, it is an instruction — and the first time it is wrong, the whole system stops being trusted. An average and a square root can be explained in one sentence each, and the screen states its own assumptions beside the answer.

MECHANISM 6The assistant

The model has no database access. It has nine tools — fixed questions like "what is on hand" or "what runs out first" — each one a closure with the tenant already bound inside it.

The loop

The provider's SDK can run the tool loop for you. This project runs it by hand, and the reason is worth knowing because it is invisible until it bites:

Streaming plus automatic function calling loses the answer

With tools declared and streaming on, the tools run and then a single empty chunk arrives marked STOP. The SDK consumes the post-tool turn internally and never re-streams it. Measured on two different models; without tools declared, the same call streams normally.

Taking the loop back has its own trap. Gemini 3 models carry a thought_signature through a turn, and rebuilding the model's turn from the function calls you read out of it — the obvious way to write the loop — drops it. A model that loses its signature re-issues the same tool call forever instead of answering. The fix is one line: echo the model's own parts back verbatim.

Three layers on the way out

LayerWhat it does
redactionIn demo mode, real SKUs are replaced with stable pseudonyms before anything leaves the process, and turned back afterwards. The provider never sees a real catalogue; the reader never sees a hash.
output filterThe answer is untrusted input. A product named "ignore previous instructions" is a note somebody typed into a form. The filter blocks claims of having changed anything, strips anything shaped like a credential, and caps runaway length.
hold-backStreaming breaks the filter's core assumption — text leaves before there is a whole answer to check. So text is released only once no rewrite can still apply to it.

Why the assistant can propose but never act

It can create a purchase order suggestion. Nothing is ordered and no stock moves until a person approves it on the Approvals screen. A wrong order costs real money, and the gap between "the model was confident" and "the model was right" is exactly where a human belongs.

MECHANISM 7Who is asking

Rate limits are easy. Deciding whose quota a request spends is not, and getting it wrong inverts the feature.

Behind a reverse proxy, the socket peer is the proxy. Counting it means every visitor on earth shares one bucket — so six failed logins from one laptop lock out everybody: 

attempt 1..5   401
attempt 6      429
real login     429   ← valid credentials, refused
after 55s      200

Nginx sets two headers that look interchangeable and are not:

HeaderDirectiveTrustworthy?
X-Real-IP$remote_addrYes — overwritten on every request, so a client cannot influence it.
X-Forwarded-For$proxy_add_x_forwarded_forNo — appends to what the client sent, so its first element is attacker-chosen.

Honouring the second would let one caller mint a fresh bucket per request by inventing an address, and the limit would stop existing. And even the safe header is only read when the peer is on a network we control — a request arriving directly is counted by its real socket. Wrong in the strict direction, never the bypassable one.

PART 3Nine real bugs, and what each one teaches

These all happened in this project. They are here because a mechanism explained is half-learned, and a mechanism you have watched fail is understood.

DEPLOYThe deploy that deployed nothing

Symptom
Pipeline green. Site unchanged.
Cause
git pull aborted because untracked files were in the way. The script carried on and rebuilt the old code.
Fix
set -euo pipefail, so a failing step stops the script.

Lesson: a shell script without set -e reports success for whatever it happened to reach last. Green means "the last command worked", not "the deploy worked".

SQLRevenue at three times reality

Symptom
A product showing ₹57 crore instead of ₹19 crore.
Cause
One query joined both sales and stock. A product on three shelves counted its entire sales history three times.
Fix
Aggregate each side separately, then join the results.

Lesson: joining two one-to-many relations in a single SUM multiplies them together. If a total looks like a suspiciously round multiple of the truth, count your joins.

SDKThe request that never happened

Symptom
A retry-on-429 that passed its tests and had never once run in production.
Cause
await generate_content_stream(...) sends nothing. The SDK defers the request to the first iteration, so the error surfaced outside the try.
Fix
Pull one chunk inside the handler, and put it back afterwards.

Lesson: a fake that raises where the real thing doesn't will confirm any belief you hold. The test must fail against the old code, or it is decoration.

SECURITYEverybody in one bucket

Symptom
A valid login refused with 429 because of somebody else's typing.
Cause
Rate limits counted the socket peer, which behind nginx is nginx.
Fix
Count X-Real-IP, and only from a hop on our own network.

Lesson: a protection that throttles everyone equally is a denial of service wearing a badge. Ask who a limit is for, not just whether it triggers.

TLSA certificate for a domain nobody visits

Symptom
None yet. The site was scheduled to become unreachable in October.
Cause
The renewal hook was written by ls /etc/letsencrypt/live | head -1. Once a second certificate existed, the stale one sorted first alphabetically.
Fix
Read the domain from PUBLIC_HOST, where it is already declared once.

Lesson: head -1 over a directory is a guess that works until the day it doesn't. Scheduled tasks fail months later, silently, with nothing having changed.

FRONTENDThe blank page

Symptom
Completely white page in a private window. Zero characters rendered.
Cause
Blocked localStorage does not return null — it throws on the property. The exception escaped during render and React unmounted everything.
Fix
Guard every access, and fall back to memory so the session still works for the tab.

Lesson: guarding the error was only half. Swallowing it left the token written and immediately not found, so nobody could log in. Degrade to something that works, not to nothing.

TOOLINGThe typechecker that checked nothing

Symptom
npx tsc --noEmit passed on code containing deliberate type errors.
Cause
tsconfig.json is a solutions file — "files": [] with project references — so plain tsc resolves no inputs and exits clean.
Fix
tsc -b, which is what npm run build already used.

Lesson: a check that has never failed has not been proven to work. Break something on purpose and watch it catch — otherwise you are trusting a command, not a result.

DATAThe inflatable hippo

Symptom
A "Featherlite Visitor Chair" illustrated with a purple inflatable hippo.
Cause
Names were kept and photographs searched for separately. "Chair" matches both.
Fix
Take the name and the picture from the same source row, making a mismatch impossible by construction.

Lesson: when two things must agree, derive them from one source rather than matching them carefully. Careful matching fails eventually; construction doesn't.

SUBTLEThe right answer in the wrong window

Symptom
Products deliberately set to "at risk" rendered as healthy.
Cause
Stock levels were sized from a 90-day sales rate; the screen computes cover over 30 days. A slower recent month buys more cover from the same quantity.
Fix
Measure over the window the reader is actually looking at.

Lesson: a rate is meaningless without its window. Two correct calculations over different periods will disagree, and neither is wrong.

PART 4How it ships, and stays up

The pipeline

git push → lint → tests (502) → docker build → deploy → health check → prune

The build runs before anything is stopped. An earlier version ran docker compose down first, so a failed build left the host with nothing serving and no way back except a manual checkout. Building first makes a failed build a no-op: the old containers are still up, still serving.

After up -d it checks for containers that exited. Without that the step was green whenever up -d returned — including when the API crash-looped on its first tick.

Migrations

23 of them, each with a real downgrade(). Only the API container runs them (RUN_MIGRATIONS=1); the relay and consumers share the same image but must not race it. A failed migration exits that container, which the health check turns into a failed deploy.

Living on a free tier

ConstraintWhat it forced
t3.micro, 1 GB RAMSix containers on one host. No room for a second replica, which is why some state is deliberately process-local.
20 GB diskDocker build cache reached 5.7 GB and nothing was clearing it. A full disk stops Postgres accepting writes — the site dies, rather than the deploy failing.
Gemini free tier20 requests per model per day. The quota is per model, so the runtime walks a chain of them, and repeat questions are answered from cache.

Backups

Nightly at 02:30: dump, verify the dump is complete, upload to S3, delete the local copy. The verification step is the point — an unverified backup is a belief, not a backup. The IAM role deliberately has no DeleteObject permission, so a compromised server cannot erase its own history.

How to read this codebase

Start with the module docstrings, not the code. Almost every file in app/ opens with several paragraphs explaining what the module is for, what was tried before, and why it is shaped this way. They were written as the decisions were made, so they record the reasoning while it was still fresh — including the versions that did not work.
