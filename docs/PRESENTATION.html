OptiStock

A multi-tenant inventory intelligence platform — flowchart and working principle.

Live system · https://optistock.duckdns.org · FastAPI + PostgreSQL + Redis + React · deployed on AWS

A warehouse has stock. Stock moves. The problem is not storing the number — it is noticing, in time, that something is about to run out, and knowing how much to order. OptiStock records every movement as an event, reacts to those events automatically, and each night turns the history into predictions.

THE WHOLE SYSTEMMaster flowchart

Everything below is one of these five paths. Read it left to right: something happens at the edge, it is written down once, and three independent consumers act on it.

PRINCIPLE 1The hardware seam

A scan is three facts: what, where, and which way. Nothing else. A barcode gun, an RFID gateway or an ESP32 with a scanner module can all produce those three facts, so any of them can drive the system without the system being changed.

Why this matters in the viva

Radio links drop and retry. If a held trigger or a retransmission deducted stock twice, the inventory would drift and no one would know which reading was wrong. The device's own reference makes a repeat harmless — the second attempt returns the first answer instead of moving stock again.

PRINCIPLE 2Write once, react many times — the outbox

When stock moves, two things must happen: the number changes, and everyone who cares must find out. Doing the second one directly creates a classic failure — the database commits, then the message fails to send, and the alert never fires. Or the message is sent, then the database rolls back, and an alert fires for something that never happened.

The fix is to write the message into the same database, in the same transaction. Either both survive or neither does. A separate process then carries it out to the queue.

PRINCIPLE 3Turning history into a prediction

Every night at 01:00 one chained job runs. It is chained rather than three separate timers because each stage reads what the one before it wrote — as independent jobs, a slow first stage would silently leave the rest analysing yesterday's data.

One subtlety worth mentioning if asked

Velocity divides by the full window length, not by the number of days that had a sale. Dividing by active days made an item that sold 10 units on one day of a 30-day window look like it sells 10 units per day — a 30× overestimate, and the system would have ordered accordingly.

PRINCIPLE 4Asking in plain English

The assistant does not have access to the database. It has access to nine tools — small, fixed questions like "what is on hand" or "what runs out first". Each tool is created for one request with the company already fixed inside it, so the tenant is not something the model can supply, mistake, or be talked into changing.

SUMMARYDesign decisions and their reasons

These are the questions most likely to be asked, and the honest answers.

DecisionWhy, in one line
Outbox table instead of
sending directly		A database commit and a network send cannot be made atomic. Writing both to the database can be.
At-least-once deliveryA duplicate can be spotted by its id and thrown away. A lost event leaves no trace to spot.
Redis Stream, not a plain listA consumer group tracks what each worker has acknowledged, so a crash mid-work does not lose the item.
One company_id on every rowOne database serves many companies. The id comes from the verified token, never from the request body.
Parquet for historyStored column by column, so "sum this one field across four years" reads only that field.
Averages, not machine learningEvery number on screen must be explainable to the person acting on it. A black box that says "order 400" is not usable advice.
